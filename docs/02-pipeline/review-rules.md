# Правила ревью

## Цель

Обеспечить, что каждое изменение проверено до попадания в main.

## Что проверяет автор перед открытием PR

- [ ] Код соответствует задаче из issue.
- [ ] Все критерии приёмки выполнены.
- [ ] Коммиты оформлены по Conventional Commits.
- [ ] Локально прогнаны линтер и тесты.
- [ ] Документация обновлена, если требуется.

## Что проверяет ревьюер

Поскольку команда из одного человека, роль ревьюера выполняет сам автор. Проверка проводится по формальному чек-листу, чтобы не пропустить важное:

- [ ] Изменения решают именно ту задачу, что указана в issue.
- [ ] Нет прямых пушей в main.
- [ ] CI зелёный.
- [ ] Нет очевидных ошибок в логике.
- [ ] Нет мёртвого кода и закомментированных блоков.
- [ ] Нет секретов и токенов в коде.
- [ ] Тесты, если применимо, покрывают новое поведение.

## Когда PR можно мержить

- Все критерии приёмки из issue выполнены.
- CI зелёный.
- Ветка обновлена относительно main.
- Автор прошёл чек-лист выше.

## Когда PR отклоняется

- CI красный.
- Не решает задачу.
- Есть нарушения DoD.

## Порядок разрешения разногласий

Для команды из одного человека конфликты не возникают. При сомнениях приоритет отдаётся критериям приёмки задачи и DoD из `docs/01-planning/process.md`.
